## 1. O que mudou em 2026 (fatos)

### T1. OS imutável deixou de ser nicho e virou padrão de infraestrutura

- `bootc` é **projeto CNCF Sandbox** (doado pela Red Hat), com blog próprio e
  comunidade ativa (`bootc.dev`).
- **RHEL 10 Image Mode é GA desde maio/2025**; o RHEL 10.2 (2026) traz
  **sealed images em Technology Preview**.
- A Fedora tem iniciativa formal **"Image Mode, Phase 2 (2026)"**: artefatos OCI
  derivados de bootc como cidadãos de primeira classe, construídos a partir de um
  **core comum sustentável**, com "experiência de desenvolvedor unificada".
- `dnf rebuild` (plugin DNF5, apresentado no DevConf.CZ 2026) reconcilia
  `dnf install` imperativo com o modelo declarativo de container.

**Leitura:** o modelo que o silver-goggles usa (imagem OCI + rebase) é o mainstream
de 2026, não uma excentricidade. O risco não é a direção, é o **ritmo**: a Fedora
está consolidando o pipeline em volta disso e quem ficar num toolchain paralelo
paga a diferença.

### T2. Selagem: UKI + composefs + fs-verity

Série de 4 posts do bootc (maio/2026) descreve a cadeia completa:

```
firmware → bootloader assinado → UKI assinada (kernel+initramfs+cmdline)
        → digest composefs na cmdline (coberto pela assinatura)
        → EROFS + fs-verity por arquivo, verificado a cada leitura (EIO se falhar)
```

Consequências práticas:

- `/etc` e `/var` continuam mutáveis por padrão, **mas** existe caminho para
  **`/etc` e `/var` transientes** (vídeo de junho/2026): cada boot começa limpo e
  verificado.
- A **Fedora publicou imagens de teste "sealed" para Atomic Desktop** em maio/2026
  (Fedora Magazine). Não é só servidor.

**Leitura:** o modelo de "`/etc` é semeado e o 3-way merge deixa a mudança local
vencer para sempre" — que é a base do `AGENTS.md` deste repo — é exatamente o que a
selagem quer eliminar. Em 2027 isso deixa de ser detalhe e vira decisão de arquitetura.

### T3. Fedora Atomic unificando em bootc

- Flock 2026 (junho): BoF **"The Future of Fedora Atomic: Unifying on Bootc and
  Shared Infrastructure"**.
- Fedora CoreOS (setembro/2026): ata "unificar CoreOS + bootc como um esforço só".
- CoreOS migrando para `bootc-image-builder`.

**Leitura:** a trilha "imagem = core comum + camadas" sai da fase exploratória.
Projetos que hoje mantêm pipeline próprio vão ter que justificar por que.

### T4. Composição por camadas OCI substituiu o fork de distro

Caso concreto e mais próximo do nosso problema: **Bluefin**.

- `package bluefin = common + branding + brew + imagem base`, cada um um OCI layer.
- Documentação oficial: *"Bluefin is a combination of a set of configuration OCI
  containers... This is opposite of the traditional Linux distribution model, the
  value is in the other OCI layers, not the base image."*
- `projectbluefin/common` tem 251 arquivos em `system_files/shared` +
  `system_files/<variante>`, e o Containerfile faz
  `COPY --from=common /system_files/shared`.

**Leitura:** é o precedente direto para o desenho L0–L4 do catálogo. E confirma que
"variante = build arg", não "variante = repositório novo" — o **bluefin-dx é
`IMAGE_FLAVOR=dx`**, 145 linhas + 10 arquivos.

### T5. A base está encolhendo; apps saem para camadas sob demanda

- O **Bazzite está removendo o Sunshine da imagem base** e movendo para instalação
  via Brew/Portal — há até um notificador no repo (`announcements/sunshine-brew.msg.json`)
  avisando usuários.
- `06-global-remove.sh` do Bazzite remove pacotes "substituídos por flatpak".
- `bazzite-dx` hoje só publica variantes **deck** (matriz de 4), confirmando o
  mesmo movimento: menos superfície por imagem, mais combinação.

**Leitura:** um silver-goggles com 223 arquivos e 177 receitas caminha contra a
corrente. E há um risco imediato: recipes que dependem de `sunshine` na base
podem quebrar quando a remoção chegar.

### T6. Toolchain: bootc/Containerfile é padrão; BlueBuild sobrevive e ganhou ponte

- `bazzite`, `bazzite-dx`, `image-template`, `bluefin`: todos **Containerfile +
  `build_files/NN-*.sh`**.
- BlueBuild continua mantido (último commit 2026-11-03; site declara estabilidade
  "as of 2026.06.05") e agora documenta **"How to use BlueBuild modules from a
  Containerfile"** — dá para manter os módulos `dnf`/`justfiles`/`files` e ainda
  assim ter um Containerfile.

**Leitura:** existe caminho de migração **incremental**, não big bang. Isso muda a
avaliação do P4: dá para alinhar o toolchain sem reescrever o build inteiro.

### T7. DX: o SO base se desacopla do ambiente de desenvolvimento

- A leitura de 2026 é explícita: *"o maior movimento de 2026 é o desacoplamento do
  SO base do ambiente de desenvolvimento"* — distrobox/DevContainers no lugar de
  instalar toolchain no host; micro-VMs efêmeras (Firecracker/Kata) para isolamento.
- O `AGENTS.md` deste harness já pratica isso (mise, `uv`, distrobox, brew).

**Leitura:** cada ferramenta que hoje entra na imagem por conveniência de DX
(Node? Python? toolchains?) é candidata a sair. A imagem deve entregar **motor**
(containers, virt, GPU, remote), não **conteúdo de projeto**.

### T8. Agentes de IA passaram a ser parte do fluxo, não plugin

- JetBrains (pesquisa mai–jul/2026, publicada em 19/08/2026): **90% dos devs
  profissionais usam agentes de código ao menos semanalmente; 68% diariamente.**
- Cursor reconstruiu a interface em abril/2026 em volta de agentes, rodando vários
  em paralelo **localmente, em worktrees, em VMs ou via SSH**.
- O padrão que emerge é: **um ambiente isolado por agente** (worktree/VM), com
  contexto indexado do repo.

**Leitura:** isso valida três coisas que este repo já tem — worktrees, NOMAD
(LLM local), MCP. E cria um requisito novo: o ambiente tem que ser **clonável e
efêmero por agente**, o que empurra para "imagem base pequena + camada de projeto",
exatamente o oposto de uma imagem pessoal monolítica.

### T9. Testar imagem como VM no CI virou ferramenta de primeira linha

- **bcvk** (bootc virtualization kit) — sucessor do `podman-bootc`; sobe a imagem
  bootc como VM via `bootc install to-disk` + libvirt, com enrolamento de Secure
  Boot para imagens seladas.
- `bootc container lint` é o lint padrão nos templates.

**Leitura:** os 196 asserts estáticos do `dx-verify` verificam presença, não
comportamento — e o próprio registro já reconhece isso. O substituto natural em
2026 é boot de verdade em VM no CI.

## 3. O que isso significa para o `silver-goggles`

| Tendência | Implicação direta |
| :--- | :--- |
| T3/T6 | O toolchain divergente é dívida **com prazo**, não preferência. A ponte "módulos BlueBuild dentro de Containerfile" permite migrar em 2 passos: Containerfile primeiro, scripts numerados depois. |
| T5 | `sunshine` está saindo da base do Bazzite. A recipe `sunshine-*` do silver-goggles precisa de plano B (instalar via Brew/Flatpak/Container) **antes** do próximo rebase quebrar. |
| T2 | O modelo de `/etc` semeado (Quadlets, `/etc/skel`, `resolved.conf.d`) é o ponto mais frágil sob selagem/`/etc` transiente. Vale migrar o que der para `/usr` e tratar `/etc` como cache. |
| T4 | Valida o desenho L0–L4, com uma correção: a camada "persona" deve ser **um OCI layer separado**, não só uma pasta — é o padrão bluefin/common. |
| T1/T9 | 196 asserts estáticos não provam comportamento. Migrar para `bootc container lint` + bcvk no CI reduz manutenção e aumenta cobertura. |
| T7 | Toda ferramenta de DX que não é "motor" (GPU, virt, remote, container) é candidata a sair da imagem e virar perfil/Brew. |
| T8 | Worktrees + NOMAD local + MCP já estão certos; o que falta é o ambiente ser **reprodutível por agente** — reforça a separação base × perfil × persona. |
| Calendário | **F45 já saiu há 5 dias.** O repo ainda rotula `44` (`alt-tags: ["stable","44"]`, `labels ... version "44"`). É a dívida mais barata de pagar agora e a que mais destrava compatibilidade com a base. |
